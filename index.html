Схема уверенного объяснения

  1. Определение — одна фраза.
  2. Как работает — 2–3 ключевых механизма.
  3. Практика — пример из автотестов или интеграционного приложения.
  4. Ограничение — типовая ошибка или trade-off.
Если не помнишь точный API или команду, сначала проговори диагностический подход и логику решения. Понимание механизма полезнее механического запоминания синтаксиса.

SQL-практикум: заказы и клиенты

6 задач на одном наборе. Сначала запрос, затем сверка с ожидаемыми строками.

Синтаксис — PostgreSQL. Создай отдельную учебную БД. Набор специально содержит клиента без заказов и заказ без клиента.

Скачать исходные данные .sql
Схема и данные
-- PostgreSQL. Учебная схема: выполняйте только в отдельной учебной БД.
CREATE TABLE qa_customers (id integer PRIMARY KEY, name text NOT NULL);
CREATE TABLE qa_orders (
  id integer PRIMARY KEY,
  customer_id integer REFERENCES qa_customers(id),
  status text NOT NULL,
  total numeric(10,2) NOT NULL CHECK (total >= 0)
);
INSERT INTO qa_customers VALUES (1, 'Аня'), (2, 'Борис'), (3, 'Вера');
INSERT INTO qa_orders VALUES
  (101, 1, 'paid', 1000), (102, 1, 'paid', 500),
  (103, 2, 'new', 700), (104, NULL, 'paid', 200);

1. Фильтр и порядок

Оплаченные заказы от 500, по убыванию суммы; при равенстве по id.

Запрос и ожидаемый результат
SELECT id, total FROM qa_orders
WHERE status = 'paid' AND total >= 500
ORDER BY total DESC, id;

101 / 1000.00, 102 / 500.00

2. GROUP BY и HAVING

Клиенты с двумя или более оплаченными заказами.

Запрос и ожидаемый результат
SELECT customer_id, COUNT(*) AS n, SUM(total) AS total
FROM qa_orders
WHERE status = 'paid' AND customer_id IS NOT NULL
GROUP BY customer_id
HAVING COUNT(*) >= 2;

Клиент 1: 2 заказа, 1500.00

3. LEFT JOIN и нулевые значения

Все клиенты и число оплаченных заказов, включая ноль.

Запрос и ожидаемый результат
SELECT c.id, c.name, COUNT(o.id) AS n
FROM qa_customers c
LEFT JOIN qa_orders o
 ON c.id = o.customer_id AND o.status = 'paid'
GROUP BY c.id, c.name
ORDER BY c.id;

Аня: 2, Борис: 0, Вера: 0. COUNT(*) даст 1 для отсутствующего совпадения; COUNT(o.id) — 0.

4. Подзапрос

Клиенты, у которых нет ни одного заказа.

Запрос и ожидаемый результат
SELECT c.id, c.name FROM qa_customers c
WHERE NOT EXISTS (
 SELECT 1 FROM qa_orders o WHERE o.customer_id = c.id
);

Вера. NOT IN (SELECT customer_id ...) опасен из-за NULL в заказе 104.

5. Агрегаты и DISTINCT

Сколько заказов, известных клиентов и какова сумма/среднее/min/max?

Запрос и ожидаемый результат
SELECT COUNT(*) AS orders,
 COUNT(DISTINCT customer_id) AS customers,
 SUM(total), AVG(total), MIN(total), MAX(total)
FROM qa_orders;

4 заказа; 2 известных клиента; сумма 2400.00; среднее 600.00; min 200.00; max 1000.00.

6. RIGHT JOIN и побочный эффект

Все заказы с именем клиента, включая заказ без клиента. Затем проверь сумму заказа 103 после оплаты через API.

Запрос и ожидаемый результат
SELECT o.id, c.name FROM qa_customers c
RIGHT JOIN qa_orders o ON c.id = o.customer_id
ORDER BY o.id;
-- После операции API, если контракт ожидает paid:
SELECT status, total FROM qa_orders WHERE id = 103;

101/Аня, 102/Аня, 103/Борис, 104/NULL. После оплаты ожидай paid и 700.00, одну запись, нужную audit-запись. Сам API здесь не реализован: это упражнение на план проверки.

Сквозная практика: проверка заказа

Учебный контракт; решения сопоставь с требованиями реального продукта.

POST /orders принимает productId и целое quantity от 1 до 99. Пользователь должен быть авторизован. Цена рассчитывается сервером. Успех — 201, id и status=created; неверное количество — 422, без сохранения заказа. Повтор с тем же Idempotency-Key не создаёт дубль.

  1. Составь тестовую модель: риск, техника, данные, слой, результат.
  2. Проверь 0/1/2/98/99/100, пустое поле, null, дробь и чужой userId; распределяй по риску, а не по числу шагов.
  3. Автоматизируй API-варианты; через UI оставь happy path и показ ошибки quantity. Фикстуры создавай независимо.
  4. Проверь БД по returned id; событие OrderCreated — по correlation/event ID. Дождись результата с deadline, не sleep.
  5. В CI сначала readiness и API smoke; сохрани HTTP/логи/DOM при падении; классифицируй product/test/environment.
Критерии хорошего решения

Есть связь с контрактом и риском; негативные сценарии проверяют отсутствие побочных эффектов; schema и значения проверяются отдельно; права не сводятся к наличию токена; повтор не создаёт дубля; UI независим; ожидания ограничены; отчёт объясняет причину сбоя. Число тестов не является метрикой полноты.
